# Package Night minimum

Admin → Pricing → **Extras → Package Night minimum** controls the minimum number of nights that qualifies a Wolfhouse stay for a package. The boundary is inclusive: with a saved value of 4, three nights do not qualify and four nights do.

## Staff workflow

1. Open Extras and edit **Package Night minimum**.
2. Enter a positive whole number of nights and save.
3. The card rereads the saved value. Reloading the page must retain it.

The field is a duration, not a euro price or an extra charged to the guest. Existing Admin Pricing permissions, tenant access checks, write switch and audit trail apply. Empty, zero, negative, fractional and nonnumeric values are rejected without replacing the prior setting.

The JSON pricing configuration contains the initial value of 7 to preserve the previous policy before staff first save. It is a configuration seed, not a duration literal in the booking rules. Staff saves take precedence through the existing pricing overlay (`policy/package_min_nights`, `metadata.minimum_nights`). No new table is required. Missing/invalid authoritative settings must not quietly restore the seed or authorize a package.

## Guest behavior

- On the supported Staff/Hermes/accommodation-vertical paths listed below, preview, quote and create use the effective saved minimum. The legacy runtime exception is not covered by this guarantee.
- Luna reads eligibility from the Staff API instead of assuming a seven-night cutoff.
- For eligible dates, missing package choice prompts package explanation and a choice, not an automatic accommodation-only quote.
- Below the minimum, requested packages are rejected without silently converting the booking to accommodation-only. The guest may choose accommodation or change dates.
- Explicit accommodation-only stays remain allowed independently of this package threshold.
- Mixed-party package selections are checked individually.
- This setting does not change deposit tiers or rewrite existing bookings.

## Legacy conversion boundary — documented exception, not live-policy acceptance

The old n8n/JS conversation chain is **not an Admin-policy-aware path** in this packet. This is a **legacy runtime exception**, not an offline-only fixture: mounted staff intake previews and automation-review endpoints call this chain, and inbound execution can reach it behind its separate write/send gates. The `dry-run` filenames do not prove offline isolation. This packet does not change routing or enable those gates:

- `luna-guest-message-router.js:runLunaGuestMessageRouterDryRun` calls `evaluatePackageNightContext` without effective config and can replace a below-seed package with `accommodation_only`.
- `luna-guest-quote-proposal-dry-run.js:shouldAttemptGuestQuoteProposal` compares against the exported JSON-seed `WEEKLY_PACKAGE_MIN_NIGHTS` before the quote engine sees any supplied config.
- `luna-guest-automation-orchestrator-dry-run.js` joins those legacy stages. Supplying config only to its quote stage does **not** align its earlier intake/conversion decision.

These are retained legacy behavior, **not evidence that an Admin save is honored**, and are excluded from this packet's supported entrypoints. Do not route an Admin-minimum acceptance test or guest conversion through that chain. Migrating its router, admission gate, copy and orchestrator together needs a separately bounded legacy-path assignment; changing only its quote engine is insufficient. This exception is documented under the approved “align or document” option, not silently represented as fixed.

The supported paths are the Staff package-preview/booking-preview/availability/create functions, accommodation vertical operations, and their Hermes plugin handlers. Availability and create preflight use the same effective configuration; commit-time availability rechecks reload policy. Trusted-config dry-run is read-only and does not accept configuration from guest transport. Pure standalone seed-only helper invocations remain offline compatibility calls, not saved-Admin-policy acceptance.

The Admin verifier exercises the real browser module, route and SQL store against an isolated PGlite database, not a deployed service. Entrypoint tests execute the production HTTP function bodies, services and vertical dispatcher with synthetic SQL seams; these are not full HTTP listener/auth proofs. Hermes tests invoke registered handlers with both synthetic receipts and receipts generated by the real JS booking-preview/create-from-plan functions, with network tripwires. The strict entrypoint seam rejects every non-SELECT, including table-initialization DDL. Commit-time policy-change tests cover both provenance and no-provenance paths. These prove local tool behavior, not a live model transcript, real booking write, or deployment.
